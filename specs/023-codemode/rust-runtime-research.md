# Rust codemode runtime research

> **Decision update (2026-10-31):** Monty is selected. [spec.md](spec.md) is the current design; runtime recommendations and integration assumptions below are historical research.

Research date: 2026-10-31. Recommendation: retain QuickJS as a candidate, but replace the old unconditional in-process rquickjs decision with a disposable, brokered worker design. Prefer QuickJS-in-Wasm (Wasmi) for the first isolation spike; compare native rquickjs behind the same process protocol before selecting the shipping engine. Durable semantics belong to Bee's driver, independently of either engine.

## Bee's actual integration contract

The old `research.md` describes a different tree. There is no `src/call.rs::run_call`, no `ToolRegistry::surface`, and no implemented `tools.http.*` family here. A provenance concept exists in the evidence system, but the old `Provenance::Child/Remote` mechanism is not an available integration seam. Do not write a spec that assumes those interfaces exist.

The relevant integration is `src/session/driver/{mod,execution,recovery,budget,journal}.rs`, `src/tools/durable.rs`, and `src/session/durable/{types,mod}.rs`:

1. Submission IDs and input admission are persisted. The bounded control queue and durable admission acknowledgement are different events. Codemode IPC receipt must not imply that an effect was admitted or completed.
2. The durable reducer emits persistence effects and gates subsequent execution/delivery on commit acknowledgement. Activation identity fences stale results; operation and attempt identity must remain host-owned. Ambiguous commit failure suspends execution and requires reopening storage.
3. `OperationSpec` contains trusted recovery policy, version, input and absolute deadline. `durable_spec` binds tool contract and current compatibility; `check_durable_compatibility` reconstructs and compares it. JS must not select recovery policy or restore authority from saved data.
4. Driver execution performs proactive escalation, authorizes/reserves, runs `execute_durable` or `execute_journaled`, settles sandbox/audit, records completion, and handles receipt publication/delivery. Inner calls must use this lifecycle. Calling `Tool::call` from a JS callback would bypass critical behavior.
5. `Budget` charges by attempt, with Reserved, Settled and Unresolved states. Interrupted/uncertain work is not refunded. Model usage can remain unknown. One outer script charge cannot hide arbitrarily many inner tool attempts; specify independent script admission and per-inner-call reservations, with explicit retry charging.
6. Recovery distinguishes `NeverReplay`, bounded `RetrySafe`, and `Reconcile`. `Found` means an exact durable result **and** a quiescent executor; `Quiescent` alone is not proof that an effect never happened. Host mode cannot establish a durable descendant boundary after a crash. Enforced-mode executor recovery uses boot identity plus cgroup directory device/inode, not PID alone.
7. Worker `Journal::begin(key,input)` commits intent, checks the input digest, returns immutable completed results, and refuses a prior intent without a result. Only trusted journal-aware tools get this capability. Recovery resumes never-started subwork only when there is no pending probe, and disables new work after cancellation/deadline.
8. The worker journal is intentionally small: `store/journal.rs` rejects more than 20 probes or records over 4 MiB. Durable types cap operations at 1024, operation payload at 64 KiB, and receipt bytes at 2 MiB. These are actual existing limits, not suggested script defaults. A generic codemode call graph cannot silently reuse this journal without revisiting its schema and bounds.
9. Delivery is at least once with a sequence cursor. Evidence receipt bytes are prepared once and validated at publication and delivery. Script-rendered text is not a replacement for an inner tool's receipt or audit.

The driver currently tracks a sequential `Step::Tools` cursor and one active operation; it is not already a nested workflow scheduler. Add an explicit persisted script/child relationship and scheduler state, or a deliberately bounded trusted composition adapter. Do not pretend nested calls fit existing state without changes. Start with serial tool dispatch: `Promise.all` may enqueue requests, but admission order, attribution and cancellation must remain deterministic and bounded.

ADR 0001 requires complete effective configuration before execution; a script cannot widen user configuration authority. ADR 0002 requires one installed host executable. A hidden `bee codemode-worker` subcommand is compatible with that ADR; requiring a separately installed runtime executable would need an explicit decision.

## What Rust projects actually do

### OpenAI Codex: direct V8, explicit runtime/host separation

The pinned [runtime Cargo manifest](https://github.com/openai/codex/blob/67f0994b532b8740f14b5b738af7b7b2a915b1d6/codex-rs/code-mode-runtime/Cargo.toml) depends directly on `v8` with `v8_enable_sandbox`. `deno_core_icudata` is a data dependency; this is **not** evidence of a `deno_core::JsRuntime` architecture.

[Runtime implementation](https://github.com/openai/codex/blob/67f0994b532b8740f14b5b738af7b7b2a915b1d6/codex-rs/code-mode-runtime/src/runtime/mod.rs) starts a dedicated thread, constructs a V8 isolate, pumps microtask checkpoints and exchanges runtime events. [Cell actor](https://github.com/openai/codex/blob/67f0994b532b8740f14b5b738af7b7b2a915b1d6/codex-rs/code-mode-runtime/src/cell_actor/mod.rs) uses an isolate handle's `terminate_execution`, cancellation and event coordination. This is explicit machinery around an engine, not automatic async integration.

[Host main](https://github.com/openai/codex/blob/67f0994b532b8740f14b5b738af7b7b2a915b1d6/codex-rs/code-mode-host/src/main.rs) exposes stdio, grpc+stdio and TCP gRPC transport endpoints. Separate host execution is therefore verified, rather than inferred from crate names; it does not mean every cell gets its own OS process. The runtime's inspected isolate creation uses default create parameters, so this inspection does not establish a per-cell heap ceiling. V8 sandbox enablement is not an OS capability sandbox or a total-process memory limit. Do not copy an unspecified memory policy into Bee.

Useful precedent: separate guest execution from trusted tool delegation, explicitly supervise runtime failure, and coordinate termination with output/event ownership. The inspected sources do not establish Bee-style durable effect reconciliation or exactly-once effects.

### Octet: directly relevant Rust QuickJS-in-Wasm implementation

[Public documentation](https://skaft.org/octet/docs/codemode/) describes a Rust launcher, Wasmi plus vendored QuickJS-WASI, a native rquickjs lane, fresh script state and watchdog process termination. Its displayed versions lag the retrieved source: the pinned manifest is package 0.9.6, Wasmi 0.47.2 and rquickjs 0.14.0; the page returned during final verification describes the earlier 0.9.5 bundle (the research fetch returned 0.9.1/Wasmi 0.46). The live documentation is mutable. Treat the page's performance table as author-reported experiments, not measurements transferable to Bee; no numbers are adopted here.

The pinned [runner](https://github.com/skaft-software/octet/blob/f14d4e4078bd75eb69d5db0ab53e1159d2ef0a46/extensions/octet-codemode/src/runner.rs) retains prepared engine state but creates a fresh session per script. Script epochs reject stale messages. Its [WASI adapter](https://github.com/skaft-software/octet/blob/f14d4e4078bd75eb69d5db0ab53e1159d2ef0a46/extensions/octet-codemode/src/wasi.rs) uses Wasmi StoreLimits, explicitly wires host imports and drives QuickJS pending jobs. Linear-memory allowance includes overhead beyond the configured QuickJS heap. A promise/message bridge makes asynchronous tool execution possible without requiring a synchronous Wasm import to await network I/O.

The [extension supervisor](https://github.com/skaft-software/octet/blob/f14d4e4078bd75eb69d5db0ab53e1159d2ef0a46/extensions/octet-codemode/src/extension.rs) has deadline/watchdog handling; the runner defines a hard-stop grace. The [native adapter](https://github.com/skaft-software/octet/blob/f14d4e4078bd75eb69d5db0ab53e1159d2ef0a46/extensions/octet-codemode/src/native.rs) sets an interrupt handler and pumps jobs under the same protocol. This refutes the old blanket claim that Wasm's synchronous imports make codemode async impractical.

Both engine dependencies are unconditional in this inspected manifest: selecting the Wasm execution lane does not itself eliminate native QuickJS build dependencies. Bee should explicitly feature-gate its comparison lanes. Wasm contains guest linear memory; the adapter, Wasmi and host imports remain trusted. Process supervision is still valuable.

### ForgeMax: actual deno_core MCP gateway

The pinned workspace selects `deno_core = 0.412`. Its [executor](https://github.com/postrv/forgemax/blob/83878b19c79d69da2d1f21b785e1b8f4f296ebe1/crates/forge-sandbox/src/executor.rs) registers Rust dispatch for `forge.callTool` and resource reads, runs V8 on a dedicated thread, and supports an optional child-process execution mode (the source describes in-process as default). It configures V8 heap limits, a near-heap callback and watchdog termination. [Host](https://github.com/postrv/forgemax/blob/83878b19c79d69da2d1f21b785e1b8f4f296ebe1/crates/forge-sandbox/src/host.rs) and pool source implement IPC, timeout handling and worker disposal. This is a useful reference for a real MCP bridge, not merely a list of recommended crates. Its AST validation is an additional policy check, not proof of isolation. These paths were inspected, not executed or security-audited.

A second Rust execution example is [leostera's engine](https://github.com/leostera/agents/blob/a9399e353ad2a7dff75e1cad509d5fc9bc5ea2dc/crates/codemode/src/engine.rs): `JsRuntime`, host extensions, custom module loader, function invocation and `with_event_loop_promise`. The inspected construction uses default runtime options apart from extensions/loader; it does not establish production heap or cancellation limits. This is an embeddable agent execution/search library, not evidence that every Rust codemode library is a hardened MCP gateway.

### Pi: adjacent precedent, not Rust

The pinned README describes QuickJS-Wasm, worker threads on Node/Bun and a separate Worker/Durable Object deployment for its remote variant. Tools return promises through JSON values. Particularly useful: the documentation explicitly distinguishes requesting worker termination from proving the worker stopped, including built-ins that do not promptly check interrupts. Bee needs the stronger quiescence distinction it already models. A Durable Object deployment and a JSON store do not establish replay-safe arbitrary external effects.

## Engine choice and current API boundaries

**Native rquickjs:** [0.14 AsyncRuntime documentation](https://docs.rs/rquickjs/0.14.0/rquickjs/struct.AsyncRuntime.html) exposes pending-job driving, memory/stack controls and an interrupt callback; futures integration supplies asynchronous host bridging. `parallel` concerns safe cross-thread access, not concurrent execution of one JS runtime. A custom allocator makes the documented memory-limit setter a no-op; feature selection must be tested. An async Tokio timeout alone cannot preempt synchronous bytecode execution that never yields. Run the engine off the driver thread, install interrupts before evaluation, and supervise the process. QuickJS is native C in this lane: limiting its heap does not contain engine memory corruption. [Upstream rquickjs](https://github.com/DelSkayn/rquickjs) documents QuickJS-NG backing and pre-generated bindings for supported platforms; native builds still involve C compilation, with bindgen/toolchain requirements depending on target/features. No universal build-size claim is justified.

**QuickJS-in-Wasm:** adds a Wasm memory boundary around the C engine and independently enforceable linear-memory growth limits. It does not cap Rust-side JSON, IPC queues or broker memory. Async uses request IDs, guest promises and a job pump, as Octet demonstrates. Wasmi interpretation avoids requiring a native JIT for that lane; Wasmtime is another possible host, not a requirement imposed by QuickJS. Fuel/epoch mechanisms are host-engine-specific and should not be claimed merely because an application uses Wasm. The inspected Octet path relies on interrupt/watchdog mechanisms. Vendoring a reproducible Wasm artifact moves C/WASI tooling to artifact regeneration rather than making it disappear. Keep hashes, licenses and regeneration instructions.

**V8/deno_core:** current [deno_core 0.413 RuntimeOptions](https://docs.rs/deno_core/0.413.0/deno_core/struct.RuntimeOptions.html) exposes extensions, module loader, create parameters and startup snapshot. Without a loader, module loading errors; the embedder chooses exposed capabilities. `deno_core` is not the complete Deno CLI or its permission model. It offers useful op/event-loop integration above direct rusty_v8. Heap limits and isolate termination still need an external owner; JS heap limits are not whole-process RSS limits. [rusty_v8's build documentation](https://github.com/denoland/rusty_v8#binary-build) describes prebuilt static archives and source builds. This adds distribution/cross-target and cache/toolchain work, but no build was performed here to quantify it. Choose it if required language/platform behavior or measured workloads justify that burden, not because a startup snapshot supplies durability.

**Boa:** [0.22 RuntimeLimits](https://docs.rs/boa_engine/0.22.0/boa_engine/vm/struct.RuntimeLimits.html) exposes loop, stack and recursion limits. These are not a complete wall-clock or allocator budget. This inspection did not verify an equivalent total heap cap or externally preemptive cancellation API; that is a qualification gap, not a timeless claim that Boa can never support them. Promise support alone does not run Rust I/O: an embedder must drive jobs and supply host functions. Pure Rust reduces native engine build dependencies but does not make resource exhaustion impossible. A child watchdog remains usable, though introducing Boa now has weaker directly examined codemode precedent than the other candidates.

No engine snapshot is a durable workflow: a heap image cannot atomically record a remote write, fence an old activation, reconcile an uncertain subprocess, publish an evidence receipt, or charge an uncertain attempt. Snapshots/bytecode caches may optimize initialization. They must not become authority-bearing recovery state.

## Concrete proposed contract

Use plain JavaScript async function bodies initially. Expose a small explicit tool catalog derived from actual registry schemas, and no filesystem/network/process/module loader capability inside the guest. Tool discovery and aliases are metadata, never authorization. Bound code, argument/result bytes, queued requests, logs, calls, heap, linear memory where applicable, and whole worker resources. Avoid clocks/randomness/imports in an initial replay experiment; make any nondeterministic inputs explicit and recorded.

Use a hidden worker subcommand with a versioned, bounded IPC protocol. The driver owns identities, grants, budgets, cancellation and records. Scope the worker and its descendants through Bee's existing host boundary; process separation by itself is not a permission sandbox. Fresh VM per script; only immutable compiled initialization may be reused. Do not pass credentials or host journal handles into JS. Reject late or foreign activation/script messages.

First release recovery should conservatively treat the script as `NeverReplay`: recover already committed completion where possible, retain every completed inner result and charge, and surface interrupted execution as unresolved when required. Do not automatically re-run the program after a crash. Completed effects survive script exceptions, output serialization failures and cancellation. Discarding script-local store writes cannot roll back those effects.

A later `Reconcile` design may re-evaluate a constrained deterministic script against committed inner results, but must validate source/prelude/engine/tool versions, each call's ordinal/name/input digest, and deterministic scheduling. Any mismatch or intent without result stops recovery. Re-evaluation may dispatch only genuinely never-started work under fresh authorization. This requires a new explicit composition journal contract; the current trusted 20-probe worker journal is not automatically a general replay engine.

Cancellation should stop admission immediately, cancel queued calls, ask active work to stop, kill/reap a wedged guest, and reconcile active tool effects independently. Killing the guest does not prove a remote MCP operation stopped. Deadline, script settlement, process exit and durable completion are separate events. Preserve receipt identity and audit even when the outer script fails. Define unawaited-call behavior explicitly: cancel pending work, retain already completed effects, and never let completion orphan unknown work silently.

## Validation spike and decision gate

1. Build only an isolated spike after agreeing the persisted composition contract. Implement one bounded broker protocol with Wasmi/QuickJS and native rquickjs adapters; no production integration or dependency change is part of this research. Keep engine differences below the broker interface.
2. Use actual available Bee tools plus a controlled side-effect fixture. Exercise await, rejected promises, caught errors, Promise.all queuing, unawaited calls, result serialization failure, empty pending promises and stale replies. Assert serial admission and attribution first.
3. Inject process death/commit acknowledgement loss before intent, after intent, after effect but before result, after completion but before delivery, and during receipt publication. Reopen the real store; verify no uncertain effect repeats, delivery cursor deduplicates, stale activation responses fail, and reservations are not refunded.
4. Exercise cancellation during CPU loops, expensive built-ins, job storms, host-call wait, consent wait and blocked IPC. Verify process exit and descendant quiescence separately from returned cancellation. Preserve Unknown for external effects without reconciliation evidence.
5. Stress guest heap and stack, Wasm memory growth, huge tool responses, host serialization, logs, alias collisions and queue floods. Confirm configured limits cover the relevant layer and that the driver stays responsive. Test the custom-allocator rquickjs feature hazard in the resolved build.
6. Build cold/offline and cross-target for Bee's actual supported targets; record toolchains, vendored artifact provenance and dependency closure. Measure startup, warm execution, CPU-only loops, representative JSON processing, broker round trips and total process-tree memory with identical fixtures and limits. Publish raw observations and environment, not borrowed benchmark numbers.
7. Ship the Wasm lane if its containment and deployment costs meet Bee's workload requirements. Prefer native rquickjs only if measured advantage warrants losing the additional Wasm boundary and OS isolation is verified. Escalate to deno_core for demonstrated compatibility/performance needs. Boa remains a future candidate pending limit/API qualification.

The decisive work is the durable broker and failure semantics. QuickJS is a reasonable engine family for Bee; choosing its binding is secondary to preserving the driver contract.

## Follow-up: Pydantic Monty

Monty materially broadens the shortlist if Python is acceptable as the model-facing language. It is a Rust interpreter for a Python subset, used by Pydantic AI Code Mode. Unlike the JavaScript candidates above, suspension at external calls and serialization of suspended interpreter state are explicit public features. This is a better architectural fit for persisted continuations, but not evidence of atomic external effects. Sources checked 2026-10-31: [project](https://github.com/pydantic/monty), [Rust API guide](https://pydantic.dev/docs/monty/quickstart/rust/), [snapshots](https://pydantic.dev/docs/monty/concepts/snapshots/), [limits](https://pydantic.dev/docs/monty/limitations/resource_limits/). These are mutable documentation, not a pinned/tested dependency selection.

The Rust API yields `RunProgress::FunctionCall`; the host supplies the result and resumes. Async calls can return pending futures and later yield `ResolveFutures`. A suspension dump includes the paused call stack. A subprocess pool provides crash isolation and parent-enforced deadlines, but the documented subprocess defaults do not set `request_timeout`: configure it explicitly. Direct Rust embedding requires `monty-alloc` and its hard ceiling for memory enforcement; direct hosts must also enforce suspension counts. Restoring a dump resets the suspension count, so Bee must preserve its own aggregate call/attempt budget across recovery.

Proposed Bee integration: persist a suspended continuation and its host-owned child operation identity before dispatch; execute that child through the durable driver; commit its result before resuming; use the same committed result when recovery restores the earlier continuation. This is a design proposal requiring explicit persistence ordering and crash tests. Unknown effects still require existing recovery policy; interpreter snapshots cannot resolve them. Authenticate snapshot provenance/integrity, constrain restore compatibility, and reauthorize host requests. Monty explicitly does not authenticate or fully validate snapshot contents.

Revised recommendation: if the JavaScript API is negotiable, evaluate Monty before committing to QuickJS. Its continuation model could avoid substantial custom replay machinery. If JavaScript is required, Monty is not a substitute. Validate supported Python behavior, Rust/toolchain compatibility, snapshot upgrades, process integration and the same failure-injection matrix before adopting it. No Monty build or benchmark was performed.

## Remaining limitations

No upstream tests, exploit tests, builds or benchmarks were run. Documentation and source disagree on Octet versions, so this report pins source separately. No claim is made about every possible Boa API, complete V8 sandbox hardening, security audit status, or exactly-once external effects. MCP cancellation and remote idempotency remain tool-specific. Old research's other ecosystem claims were not revalidated wholesale; they should not become spec requirements without fresh evidence.
