# Threat Model: bee

## 1. System context

bee is a Rust workspace that gives AI coding-agent tools capability-scoped access to a Linux host. Its security-critical path parses declarative policy, proves child-policy attenuation, resolves host identities and destinations, builds an eBPF-specific `EnforcementPlan`, attaches BPF LSM programs, creates a cgroup per scope, and enforces file-open, executable, and IP-connect decisions in the kernel.

The workspace also includes a harness for prompts, external model providers, built-in shell/file tools, local and remote MCP servers, transcripts and audit, CTF evaluation, in-process rendering, and work-in-progress `SKILL.md` discovery and capability grants. Intended users are agent operators, framework integrators, and evaluation researchers. Production enforcement requires Linux BPF LSM/BTF/cgroup v2 and a privileged loader; the default harness build is process-hardened and credential-stripped but not kernel-confined. This analysis covers the current dirty worktree, including uncommitted skill support.

The intended authority model is a protected, user-owned bee configuration: absent an explicit grant, access is denied; users may deliberately grant broad authority; and agents or repository content may request but cannot silently widen that authority. Launch-configured or directly invoked skills are explicit instruction choices, while capability changes require HITL approval and remain bounded by attenuation. MCP servers also require explicit configuration: bee-spawned servers belong inside the enforced scope, while pre-existing local or remote servers are outside bee's semantic control and bee owns only connection, credential, tool-visibility, and consequence-containment boundaries.

## 6. Open questions

- [Owner-states] Users may run bee against untrusted or trojan repositories. Affects: T5 actor/likelihood, T9 actor/likelihood. Verify by: document this deployment assumption in the product security contract and test repository-originated config/skill flows.
- [Owner-states] The intended filesystem model denies every read/write absent an explicit grant from protected user configuration. Affects: T4 impact/likelihood/status, T10 impact/likelihood/status. Verify by: end-to-end policy tests for unmatched reads/writes and every supported filesystem operation.
- [Owner-states] Agents cannot modify the authority configuration except through HITL escalation. Affects: T1 status, T5 status, T9 status. Verify by: integration tests proving direct writes and non-HITL policy mutations fail.
- [Owner-states] A project skill is trusted only when selected in launch configuration or directly invoked; every capability widening still requires HITL and attenuation. Affects: T9 controls/status. Verify by: launch, dynamic invocation, shadowing, and grant-path tests.
- [Owner-states] Bee-spawned MCP servers must receive equivalent enforcement; pre-existing local/remote servers require explicit configuration and their semantics are outside scope. Affects: T6/T7 threat boundary. Verify by: cgroup-membership tests and documented external-server trust semantics.
- [Owner-states] Denied DNS destinations may become review suggestions but must never mutate allowlists automatically. Affects: T11 controls/status. Verify by: policy-update tests requiring an authenticated HITL decision.
- [Owner-states] Any detected audit loss invalidates an episode's enforcement evidence. Affects: T15 impact/status. Verify by: kernel/userspace drop accounting and episode-status tests.
- [Owner-states] Enforcement compilation and the live BPF-LSM matrix must become mandatory release gates. Affects: T8/T17 status and recommended mitigation. Verify by: protected-branch CI configuration and a failing-gate rehearsal.
- [Owner-states] Transcript protection at rest is currently the operator's responsibility. Affects: T14 status. Verify by: operator documentation and a later decision on default file permissions.
- [Owner-states] In-process restricted Rhai is an accepted boundary for untrusted visualization scripts. Affects: T16 impact/status. Verify by: continued resource-limit and API-surface regression tests.
- Production child identity remains unknown: the code does not visibly drop uid/gid, supplementary groups, or capabilities before exec. Affects: T2 likelihood/status. Verify by: inspect deployment wrapper and record runtime credentials/capability sets in the VM matrix.
